# witness v0.47.0: plan (bets against the North Star)

Status: **draft for the owner's review**. Planned at main `b041995`, last tag `v0.46.0`. This is work in progress. witness produces MC/DC-style evidence on lowered WebAssembly; nothing here is a certification or qualification claim.

How this plan was made: a planner drafted five bets from `data/north-star.toml` (pulseengine.eu), the rivet state, the open issues, the v0.46.0 notes and the seams. A second reviewer, with a cold context and only `north-star.toml` and the draft, checked each bet for indicator movement, falsifiable acceptance, overclaiming and busywork. Every bet came back "keep with changes". This document is the draft with those changes applied.

## What this release does and does not move

**No North Star indicator number changes in v0.47.0 because of witness alone.**
- O2 stays at 1 of 2 consumer repositories until relay ships a bundle.
- O3 and O5 stay "unmeasured" until pulseengine.eu has indicator scripts for them.

What witness can do is (a) change what "passes the verify command" means for the MC/DC part of a bundle, (b) put itself into the population the O3 and O5 indicators will count, and (c) stop the tool from reporting a clean 0/0 on decisions it cannot see. Every cross-repo step a number depends on is listed as a seam issue to open (an acceptance item), not as an assumption.

The owner asked that bets making witness's MC/DC evidence re-checkable by an assessor (O2/O3) count double. That weighting is the owner's priority; `north-star.toml` itself does not say it.

## Sequence

1. **Spikes, about two days each, before any bet starts:**
   - S1: can a run record plus manifest re-derive `report.json` with no hidden input (DWARF, source paths, environment)? This gates Bet 1.
   - S2: can kiln run a wasip2 command component with a preopened directory and return its exit code? This gates Bet 2.
   - S3: does the existing meld fusion path give a non-empty MC/DC report on wohl's composed component? This gates Bet 4's scope.
   - S4: Kani or Verus, which one handles the checker kernel at useful bounds in CI time? This gates Bet 5.
2. **Bet 3a** (last operand), then **Bet 1** (recheck), then **Bet 5** (kernel proof).
3. **Bet 2** and **Bet 3b** only if their spikes or measurements pass.

Cut order if capacity is short: 3b first, then 2. Bet 4 is S-sized after re-scoping and stays.

**Traceability.** Each bet lands as a rivet feature with `release: v0.47.0` and status `draft`. The rivet pinned here does not know a `serves:` field yet, so each feature names its objective in its description and in a `serves-Ox` tag until `serves:` ships.

## Bet 1: `witness recheck`, internal consistency an assessor can re-run

**Serves:** O2.

**What ships.** `witness recheck <evidence-dir>` checks, without access to the build:
- (a) every file against an inventory that is written before archiving and compared after;
- (b) the hash chain from instrumented module to manifest, run record, report and predicate subject;
- (c) that `report.json` re-derived from `run.json` plus the manifest, through the `witness-mcdc-checker` kernel, equals the shipped report.

The compliance action emits that inventory, generates its README from it (fixes #360), and stops swallowing failures. recheck states in its output what it shows: the report follows from the shipped run record, and the bundle is internally consistent. It does not show that the run record came from a real execution, or that witness itself is correct.

**Indicator.** O2: "passes the verify command". For the MC/DC part, recheck turns a text match into a re-derivation. The count stays 1 of 2. The O2 guard ("must fail when any piece of evidence is removed") gains a control that only re-derivation catches, once the seam below lands.

**Grounding.**
- #360 (static README heredoc, `.github/actions/compliance/action.yml:169-200`).
- Fail-open steps at `action.yml:97`, `:112`, `:129`, plus the self-verify step at `:142-159`.
- `witness verify` checks a DSSE signature with a key that ships next to the envelope (`crates/witness/src/main.rs:278-310`).
- The reporter already calls the kernel (`crates/witness-core/src/mcdc_report.rs:1313-1321`).

**Acceptance (can fail).** A required CI job `recheck-controls`:
1. recheck exits 0 on verdict-suite evidence.
2. Planted controls in `ci-controls.toml`, each non-zero with a distinct message:
   - a deleted `run.json`;
   - a flipped byte in `instrumented.wasm`;
   - one condition edited from `gap` to `proved` with hashes and inventory re-computed;
   - an inventory line for an absent file;
   - a bundle re-signed with a fresh key, which must fail against the expected signer identity. That identity comes from the release's keyless cosign certificate, a trust anchor outside the bundle.
3. One control per fail-open step: a failing `run-suite.sh` (and each other step listed above) must turn the compliance action red.
4. recheck on linux x86_64 passes against evidence produced on macOS aarch64.

**Kill criterion.**
- If S1 finds a hidden input, re-scope to hash-chain and inventory checks only, and state that in recheck's output.
- If canonical-JSON equality is not stable across the release matrix within the S1 time box, compare verdict fields semantically. If that needs per-platform exceptions, drop (c).

**Seams to open (acceptance items).**
- wohl: replace its `grep '^gap-total: 0$'` verify step with `witness recheck`.
- pulseengine.eu: add the "edited verdict, hashes re-computed" control to `scripts/north-star-o2.py`.

**Size:** M if S1 holds, L otherwise. **Riskiest assumption:** S1.

## Bet 2: the schema gate as a signed WASI component under kiln

**Serves:** O5. Runs only if S2 passes.

**What ships.** `tools/check_report_schemas.py` (73 lines, the named "no new Python" port candidate) ported to Rust and built as a wasm32-wasip2 component. CI signs it with sigil, verifies the signed bytes with `wsc verify`, and runs those same bytes under kiln and wasmtime. The bet does not include Bet 1's recheck logic, which has no old version to be equivalent to.

**Indicator.** O5: "tools and CI gates that run as signed WASI components under kiln, with wasmtime as the differential". The bet adds witness's first gate that could count. It also adds a `gates.toml` listing every required check and how it runs, which is the denominator an O5 script needs. O5 stays unmeasured until that script exists.

**Acceptance (can fail).**
1. CI signs the component, verifies it with `wsc verify` (a one-byte-flipped copy must fail), then runs the verified file under kiln and under wasmtime on `tests/fixtures/report-schema` and on verdict-suite evidence. Exit codes and per-file verdict lines are identical across both runtimes and the Python checker.
2. Plant `report-schema-extra-property` goes red under both runtimes.
3. The equivalence oracle outlives the Python. Before the script is deleted, its verdict lines on the fixtures and on a mutated-report corpus (undeclared field, wrong type, missing required field, unknown schema URL) are frozen into a checked-in expected file. CI compares the component against that file on every run.
4. A CI step fails if `gates.toml` differs from the branch protection's required-check list.

**Kill criterion.** If S2 fails, drop the bet. A wasmtime-only Rust port moves no indicator and waits until a Python change triggers it. Also drop it if a Rust JSON Schema 2020-12 validator for wasip2 disagrees with the Python validator on any corpus file.

**Dependencies.** kiln (S2), sigil `wsc` (exists), varve (provides kiln and wsc to CI).

**Size:** M.

## Bet 3a: observe the last operand of a short-circuit chain (#358)

**Serves:** O2. It moves no indicator; it keeps an O2 bundle from passing with a report whose decisions witness cannot see.

**What ships.** #358 steps 2 and 3: row outcomes from the return-value trace, and a probe on the value produced by the last operand.

**Acceptance (can fail).**
1. The 4 `missing-last-operand` entries in `verdicts/TRUTH-TABLE-DIVERGENCES.json` go stale and are removed. `triangle`, `leap_year`, `state_guard` and `safety_envelope` no longer report `unobserved_tail_conditions`.
2. Ledger rule in CI: at most 13 entries on every PR (13 at `b041995`), at most 5 at the release tag, and no entry may change category between the merge base and the head.
3. `tests/no_overclaim.rs` stays green, and a planted control (the probe mapping perturbed by one condition index) turns the truth-table check red.

**Kill criterion.** Stop if the value probe changes any non-ledgered verdict's proved pairs, or adds any `false-proved` divergence that cannot be fixed within the bet's time box (two weeks).

**Size:** M.

## Bet 3b: decisions lowered to branch-free arithmetic (#268, REQ-079)

**Serves:** O2 (same reason as 3a). Runs after 3a.

**What ships.** Probes on the comparison results feeding an `i32.and`/`i32.or` tree. Where a decision cannot be recovered, the manifest carries a warning instead of a clean 0/0.

**Acceptance (can fail).**
1. The verdict suite runs as two required jobs on two named rustc versions, 1.98.1 and 1.99.x. A non-required canary runs on floating stable.
2. The 4 `condition-count` ledger entries go stale and are removed, under the same ledger rule as 3a.
3. `range_overlap` and `mixed_or_and` either leave the `ZERO_DECISION` tier of `tools/check_truth_tables.py` with real comparisons, or carry the warning. recheck (Bet 1) and `witness verify` must not report a clean pass when the warning is present.

**Kill criterion (mechanical).** On `httparse` and `json_lite`, count new decisions whose DWARF line has no `&&`, `||` or comparison token in the source line. If the count is above zero and cannot be filtered without a per-fixture rule, ship only the warning.

**Size:** L. **Riskiest assumption:** that a decision's boundary is recoverable without branches.

## Bet 4: decide and test the component path for MC/DC (re-scoped to S)

**Serves:** O2. The 2027-Q1 relay stretch: "relay's release adds the MC/DC part, which needs witness to read component modules".

**What ships.**
1. Spike S3: run the existing meld fusion path (REQ-054) on wohl's composed component (wohl#58) and record the decision count.
2. A written decision on whether a report on a fused core module counts as a component's MC/DC part, and how the report is bound by hash to the shipped component.
3. A fixture test for whichever path works: a wasip2 component with a 3-condition decision and a hand-derived truth table, giving one decision with the correct condition count.
4. A wohl job that is required once wohl confirms the floor: more than zero decisions, and no 0/0 without a warning.

The native per-row component run path (REQ-060 is counters-only) moves to v0.48.0, and only if fusion is insufficient.

**Kill criterion.** If fusion gives a usable report, the native path is closed as unnecessary. If neither path gives a non-empty report on wohl's component, say so in the release notes and open the v0.48.0 bet.

**Dependencies.** meld (exists), wohl (seam wohl#58), kiln (only for the deferred native path).

**Size:** S.

## Bet 5: bounded proof harness for the checker kernel, with an audited ledger

**Serves:** O3. It is the only bet shaped like the O3 indicator: a proof check, a kernel axiom audit and a trust-escape ledger, run as a required check.

**What ships.** A Kani or Verus harness (chosen by S4) for `find_independent_effect_pair` in `crates/witness-mcdc-checker/src/lib.rs:111-186`. It checks soundness, completeness and the unique-cause preference against a specification written as a standalone declarative predicate. A reviewer other than the author signs off the predicate. A ledger file lists every assumption, and the proof job becomes a required check.

**Acceptance (can fail).**
1. The required proof job exits 0 and states its row bound and its condition bound.
2. Four planted kernel mutants each make the proof fail:
   - the outcome-differs check removed;
   - the non-target compatibility loop skipped;
   - the unique-cause preference inverted;
   - completeness broken: return `None` although a pair exists.
3. Axiom audit: a CI step extracts every `assume`, unwind bound, stub and model (a `BTreeMap` model counts as one) from the harness. The step fails if that list differs from the ledger, if the ledger grows, or if a bound falls.
4. Bootstrap: the first ledger commit is the baseline, reviewed in the PR that adds it. After that, the shrink-only rule applies.
5. The README's "qualifiable kernel" sentence is bound to the job through a `claims.yaml` entry.

**Kill criterion.**
- Drop if the proof does not terminate at a condition bound of at least 5 (`safety_envelope`) within the job's time limit.
- Drop if the harness needs a model so far from the shipped code that the proof is about another function.
- Drop if any mutant passes.

**Size:** M after S4. Unsized before.
